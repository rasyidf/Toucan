# v0.24 roadmap implementation audit

The visual refinement work completed the v0.24 editor/onboarding implementation and a few tasks previously left in the future backlog. It did not complete the later product milestones. This audit compares the current `release/v0.24.0` source with the [roadmap](../todos/future-roadmap.md), including production callers, persistence and existing behavioral tests. A model, command flag or settings control alone does not establish a finished workflow.

## Completed work removed from future planning

| Main plugin command toolbar | `TranslationEditorView.axaml` renders `ContributedToolbarActions`; `MainWindowViewModel.EditorComfort.cs` derives command state from the registry. `EditorComfortTests` exercises a rendered contribution and command outcomes. | Remove the deferred global toolbar task. It is implemented in the v0.24 source build. |
| macOS native menu bar | `MainMenu.Attach` exports and refreshes a native menu on macOS, filters project commands and refreshes native shortcut ownership; project menu tests cover registry visibility. | Narrow the deferred platform item to system-accent integration. Custom color schemes do not establish system-accent following. |
| Rule settings UI | `OptionsViewModel` enumerates built-in/plugin rules and saves enable/severity preferences; `ValidationPageTests` verifies plugin-rule discovery. | Do not build a second settings editor. Track runtime enforcement under v0.25/APP-06; remove its duplicate deferred plugin task. |
| Manual update channels | `UpdateService` filters draft/prerelease records and selects an eligible version; About exposes the manual check. | Narrow v0.30 to the remaining startup checks, changelog presentation and distribution work. |

## Documentation overclaims corrected

`ValidationPipeline.RunAll` invokes all registered rules. The manual validation, save, approval and workspace-edit paths do not apply stored enable/severity overrides. `CustomValidationRule` implements a rule type, but no production project rule-file loader/registration path was found. These are source findings, recorded as [APP-06](../known-bugs.md#app-06), rather than a newly reproduced runtime test. The capability list and README no longer describe complete configurable project validation.

The translator guide previously claimed nested ICU syntax validation prevented corruption. Current inline warnings cover named-double placeholders, while `PlaceholderMismatchRule` compares regex token counts. Spelling's ICU-aware text extraction skips syntax; it does not validate a message grammar. The guide now keeps the v0.25 grammar work explicit. The unconnected VCS panel model is also removed from the list of complete Git capabilities.

## Regression fixes and verification

The audit reproduced two regressions: stale source placeholder context after edits/rename, and a read notification badge returning on project-summary refresh. Card rows now update their target source context through property-change notifications, with subscriptions removed on disposal; plural variants remain independent. Notification history totals remain available separately from the unseen badge.

Focused verification passes 33 tests, including direct source edits before save, rename/undo/redo, plural context, target-focus workflows and notification summaries/new arrivals. The full UI suite and final results are recorded in [editor acceptance](../specs/editor-comfort/acceptance.md). The external connector test still requires `TOUCAN_EXTERNAL_CONNECTOR_DIST`; it is not silently accepted or removed.

## Planning recommendation

Keep v0.24 focused on finishing editor acceptance and the two fixes above. Keep v0.25 next, with runtime validation policy applied consistently before adding glossary-dependent rules. Reuse the existing identity, transactions, review UI and connection-scoped services in later milestones; do not count them again as features to build from scratch. Retain the later completion gates until persistence, callers and complete user workflows meet them.

During beta, each minor version replaces the previous development branch. Tags and published pre-releases preserve older versions; parallel maintenance branches are reserved for major-version maintenance.
