# M5 and M6 framework integration

M5 and M6 were implemented consecutively, preserving the pending M3/M4 work. Framework modules supply optional settings and scanner companions through existing dependency injection. File providers supply optional editing capabilities. Core owns workspace enforcement, exact resource dispatch and scan orchestration. No installed BabelEdit file, vendor implementation, artwork or new dependency was used.

## M5: framework capabilities and generated catalogs

`IFrameworkProfile` is unchanged. Optional `IFrameworkFeatures` supplies a scanner ID, the existing `ConfigSchema` and an exact resource description. Old profiles keep their discovery and default behavior. Existing profiles retain their registration order; new profiles follow them. `IResourceCapabilities` and neutral resource ownership govern editing independently of the framework's display name. The 14 existing editable format IDs remain unchanged; `formatjs` is an additional generated-catalog format rather than a legacy enum renumbering.

Generated source permissions block value, comment, approval, audit and key changes. The editor and command registry show restrictions; direct structural commands, bulk operations, workspace/plugin plans, general and spreadsheet imports and CLI edits also enforce them. Exact saves compare protected entries against their source before allowing writes, so bypassing the model API cannot overwrite or delete generated messages. Empty generated documents remain protected. Ordinary target values are editable, and missing target entries can be populated from existing extracted IDs without creating source keys. Changing a generated project's language/resource layout requires configuring its target descriptors; the normal add/remove language commands are refused.

The FormatJS reader accepts ID-to-descriptor objects with string `defaultMessage`, optional string/object `description` and opaque additional fields. IDs remain literal keys. Generated documents retain their original bytes and are never serialized as ordinary editable JSON. Target catalogs use literal ID-to-string JSON. Compiled AST source/target catalogs are explicitly unsupported and produce diagnostics rather than editable AST nodes.

The native `formatjs` profile discovers generated `extracted/*.json` and editable `locales/*.json` targets. Native descriptors support other exact paths. The import wizard validates a new profile's resources before writing its native manifest, respects existing native settings, and leaves the active project intact on invalid input. i18next profile import describes JSON resources by package and declared language while retaining its old profile interface/default format. The compatibility module also maps supported original `react-intl`/`formatjs` projects to neutral generated-source/target roles. Unknown external configuration keys and unsupported option values are diagnosed and preserved in the compatibility envelope.

Save/reopen retains permissions and metadata. Save As copies generated originals byte-for-byte using the existing lifecycle and refuses a conflicting generated destination. Framework options and scan settings travel with the copy.

## Supported settings

Framework project properties reuse `ConfigForm`, `ConfigSchema` and the existing validation implementation. A detached `FrameworkConfiguration` edits native typed options; cancelling the properties dialog leaves the project's options unchanged.

| Native option | UI label | Behavior |
|---|---|---|
| `defaultPackage` | Default source package | Package for source keys without an explicit namespace; default `main` |
| `resolveNamespaces` | Resolve source namespaces | Resolve supported explicit namespaces and static scope bindings; disabling it matches raw keys in the configured default package |
| `keyPrefix` | Source key prefix | Optional prefix for static keys |

Only profiles supplying the companion schema expose these options. Future native option fields are preserved and diagnosed by scanning. External option names stay in the compatibility module.

During verification the pre-existing settings-form test reproduced the asynchronous file-lock race recorded at M4: its in-memory assertion could run before persistence finished. It now waits for the existing `Changed` completion notification. Saving one form field also refreshes that field only, preserving another field's uncommitted draft; the existing workflow test now verifies this behavior.

## M6: source requests, extraction and references

`ISourceScanner` operates on bounded file text and returns references and structured diagnostics. `IProjectSourceCodeService` selects a registered scanner through framework features and carries project roots, globs, excludes, extensions, package context and resource-key mappings. The original `ISourceCodeService` methods remain available; legacy construction has a generic fallback with explicit limits.

References include package, raw key, typed path, relative file, UTF-16 offset, one-based line/column and source-line text. Matching uses package/key identity and maps back to workspace display names. Equal textual IDs in different packages stay separate; ambiguous literal/nested resource matches are findings. Unknown packages are diagnosed rather than matching every package. The UI uses project-relative paths for navigation across all configured roots and supports the editor template's `{column}` placeholder.

The parser tokenizes strings, escapes, comments, delimiters and template/code boundaries. It handles multiline calls and balanced arguments instead of applying a line regex. Static extraction follows these original fixture subsets:

| Scanner | Verified syntax |
|---|---|
| i18next | `t`/`i18next.t`, options including `ns`, colon namespaces, fallback key arrays, single static `useTranslation` namespace/key-prefix binding |
| Transloco | `translate`/`selectTranslate`, structural `t`, pipes, attributes and bound inputs; current `prefix` and legacy `read` as key prefixes; simple static scopes |
| Vue i18n | `t`/`$t`/plural variants, interpolation and bound attribute expressions, `v-t` literal expressions and `i18n-t keypath` |
| Rails | String and symbol translation calls, multiline options, string scope and view-relative keys, including partial-name normalization |
| React / FormatJS | `formatMessage`, `defineMessage(s)` and `FormattedMessage` with explicit static IDs; nested description IDs are not message IDs |

Quoted examples, comments and plain template text do not become function calls. Dynamic expressions, unresolved/renamed/multiple bindings, unsupported scope/alias objects, descriptor spreads and automatic FormatJS ID generation remain findings. This is a bounded static parser, not a JavaScript/TypeScript/Ruby compiler or framework execution engine. Cross-file data flow, arbitrary wrappers/macros, complex imported bindings, implicit Rails model lookups and arbitrary scope transformations are outside the verified subset. Unsupported constructs recognized by the parser disable unused-key classification. Interpolated strings are conservative unresolved findings, including expressions that could contain nested translation calls. Users must review the supported subset before treating an unmatched key as removable; this milestone adds no automatic deletion of source-unused keys.

## Scope, limits and cancellation

Project properties persist all source roots, extensions, path includes and excludes. Empty includes mean the default source scope, not an empty scan. Globs use bounded non-backtracking regex. Default dependency/build folders are skipped. Reparse points and directory cycles are never followed; links, unreadable files, missing roots and truncated work produce explicit diagnostics. The shared resource enumerator was also fixed to skip links, because CLI project discovery occurs before source scanning and otherwise could loop before the scanner started.

Limits are 20,000 source files, 50,000 directories, 2 MiB per file, 100 MiB total source bytes, 128 configured roots/include/exclude patterns, 512 characters per glob, 300,000 lexical tokens and two million delimiter-parser steps per file, eight embedded-expression levels and 200,000 accumulated references. Reads are bounded again after opening the file to handle growth races. Cancellation returns a partial result marked cancelled. Cache replacement is guarded against stale scans and project changes.

The source panel shows references and diagnostic messages, provides cancellation and disables unused-key classification when the scan is incomplete, cancelled or unresolved. Known references from a partial scan remain visible. The generic fallback can show references but cannot certify unused keys. There is no destructive cleanup command derived from an incomplete scan.

`toucan scan <folder>` returns JSON references, diagnostics, completeness and duration. Exit 0 means the supported scan completed without unresolved findings; exit 2 means its result cannot classify unused keys. Existing CLI edits still use the normal project/save services.

## Executed verification

The complete Windows solution run passes **1,342 tests**: Core 1,060, Avalonia 271 and plugin harness 11, with no failures or skips. This includes eight new capability/catalog cases, 51 scanner cases and four new headless framework integration workflows. The existing settings-form test was strengthened. General format round-trip fixtures still exercise all 14 editable formats; generated catalogs have separate preservation and refusal tests instead of being treated as creatable export formats. Registration snapshots explicitly include the additive format/profiles. The frozen M0 sample plugin remains unchanged and passes.

Production headless composition covers profile import validation, preservation of an existing native project, generated edit/rename/delete/add/bulk/workspace refusal, editable and missing targets, native reopen and Save As, registry availability, multiple source roots, locations/navigation, missing keys and disabled unused filters after dynamic expressions.

CLI checks verify one-way original FormatJS migration, source/add-key refusal, target edits and native reopen without the migration file. They also exercise dynamic findings, default excludes and a real Windows junction cycle. The final original benchmark has **200 files, 324,490 source bytes and 10,000 references**; the recorded Debug run took **1.009 seconds in the scanner and 1.431 seconds including CLI process startup/project loading**. This is one machine/run, not a cross-platform performance budget. The 19 original corpus scenarios, six exact-resource migrations and four resource-fidelity CLI cases were rerun successfully.

[Machine-readable suites, CLI measurements, earlier failed attempts and source fingerprints](evidence/m5-m6-verification.json) record acceptance. Initial integration failures exposed registration snapshots and writable-format fixture assumptions; these were updated to use capabilities. The reproduced settings-test race and its correction are retained in the verification history.

Verification covers Windows x64, .NET 10.0.401 and Avalonia headless. Native OS pickers, packaged GUI behavior and other platforms were not executed. The existing AVLN3001 MainWindow constructor warning remains. M3–M6 are uncommitted; earlier milestone evidence was not regenerated. M7 spelling/provenance and the final cross-platform release gate remain open.
